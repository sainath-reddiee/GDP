Operating guide

GDP Agent Platform Guidebook

Everything needed to run the platform: who can do what, which Snowflake grants back it, how to configure each feature, and what every table holds. Written for data engineers, QA, support engineers and platform admins.

01How access works

Every action passes two independent checks. Both must allow it.

1. App governance

The API maps each call to a privilege (for example STTM.APPROVE). A user's privileges are the union of their app roles, including inherited roles. Roles live in the GOVERNANCE schema and are managed in Admin, Access and governance.

Each call is decided as Allow, Request (HTTP 202, queued in Approvals) or Forbid (HTTP 403).

2. Snowflake grants

The call then runs on a Snowflake session. Snowflake enforces its own object grants on the session's current role. A user can switch that role with the role selector at the bottom of the sidebar; only roles granted to the user are offered.

An approved request is replayed under the approver's session, so the approver's grants apply.

Decision rules

  • Allow when the call needs no privilege, or the user holds it and its approval policy is off (or the user may self-approve).
  • Request when an approval policy is active and the user holds REQUEST.CHANGES or the privilege itself under a four-eyes policy. The UI shows the action and says it was sent for approval.
  • Forbid otherwise, with the message "needs the X privilege".
  • A changing call (POST, PUT, DELETE) that no rule names needs RUN.OPERATE. A GET that no rule names is open to every signed-in user.
  • Role changes take effect within about a minute (60 second cache).
  • Until migration V020 is deployed, governance is not enforced.
First admin. When nobody holds any role yet, the first person to sign in, plus everyone listed in AIP_SUPER_ADMINS, becomes SUPER_ADMIN. Everyone else without a role gets the default role, VIEWER unless changed in Admin.

02Setup order

For a new environment, do these in order. Each later feature depends on the earlier steps.

  1. Deploy Snowflake objects. Run python infrastructure/deploy_snowflake.py --connection <name> --database DEV_AI_PLATFORM --warehouse DBT_WH with a role that can create schemas, procedures, stages, Cortex Search services and agents. Always pass --database: the script's default (AI_PLATFORM) differs from the API's (DEV_AI_PLATFORM).
  2. Grant database roles to account roles. See Who gets what. Also grant warehouse USAGE and SNOWFLAKE.CORTEX_USER.
  3. Configure the API. Copy apps/api/.env.example to apps/api/.env (gitignored) and fill it in, or, with Docker, docker/api.env.example to docker/api.env. See Environment variables.
  4. Start the API and web app, then sign in once with an admin account so governance bootstraps. Set AIP_SUPER_ADMINS first if the first sign-in should not be you.
  5. Assign app roles in Admin, Access and governance.
  6. Connect integrations in Admin, Integrations: code repositories and GitHub publishing, Jira, Airflow, Incidents.
  7. Start the worker (python -m app.worker in apps/api) if you use Pipelines or Incidents. With Docker the worker container starts with the others.

04Features

The sidebar is the one place to move around, in lifecycle order: Overview (the Command Center, the Copilot workspace and Tickets), Onboarding (a highlighted entry of its own: sources, domains, applications), Asset stores (Store, one item over the six asset stores: Source, Profiling, Modeling, Mapping (STTM), QA and Data Quality), Knowledge (domains, knowledge, skills), Build (runs, code), then Monitor (Quality center, QA testing, pipelines, incidents) and Govern (approvals, source control, audit, admin). Monitor and Govern can be folded to their heading; the choice is remembered per browser, a section opens by itself while you are on one of its pages, and a folded heading shows the summed badge of its links (pending approvals, for example). Clicking Store opens the Store hub (/dashboard/store): one card per store with what it holds and what needs action. Its chevron shows the six stores underneath, opened by itself while you are in one of them; with the sidebar collapsed, hovering or focusing the Store icon opens a menu of the stores. Store stays highlighted inside any store, and its badge sums the stores that need attention (each store keeps its own badge). Every store page has a bar to switch stores that keeps an explicit ?domain=; the domain picked in the top bar applies everywhere. /dashboard/store?tab=sources|profiling|modeling|sttm|qa|quality opens that store, and /store, /dashboard/qa, /dashboard/data-quality, /dashboard/mapping, /sources and /onboarding redirect to their pages. Run pages under /runs/<run id> are unchanged. A group disappears when none of its pages are available to the user.

Sources

Page

Share onboarding
Pick a mounted share database (or mount one with the provider account and share name, which needs IMPORT SHARE), a schema and tables. One action creates a run and takes it through register, access and landing: each table is unloaded once to Snappy Parquet on SOURCE.LANDING_STAGE, the landing table is created with the source's exact types and filled with COPY INTO ... MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE (procedure SOURCE.EXECUTE_STAGED_LANDING). The run then continues on its own pages.
External sources
Every system outside Snowflake (Oracle and other databases, Salesforce, REST, files and cloud storage) is landed by SnapLogic. The SnapLogic wizard in Onboarding writes PLATFORM_CONFIG.INGESTION_CONTROL_CONFIG; intake answers become a row of PLATFORM_CONFIG.INGESTION_PIPELINE_CATALOG (questions from the platform setting INGESTION_INTAKE_FORM, editable through PUT /api/hub/intake-form; secret answers are encrypted with AIP_SECRET_KEY). The External sources panel appears only when a configuration or a pipeline exists. It lists the ingestion configurations by master ID (open a row for its history, switch a table on or off; every change is kept in INGESTION_CONTROL_HISTORY) and the registered pipelines with their status. The platform never calls SnapLogic.
Snowflake catalog
Pick a database and schema, select tables, Profile (only tables without a current profile) or Profile all from scratch. Profiling runs where the data lives and never copies it. "Start modeling" creates a run from the selection.
Earlier connectors
The in-app file upload, cloud storage and Oracle connectors were removed. Tables they already landed stay in <db>.EXT_<SOURCE> and can be browsed and profiled in the catalog; their Snowflake objects (stages, secrets, integrations, Oracle procedures and tasks) and API endpoints remain until an admin drops them.

Profiling hub

Page
/dashboard/profiling
What it does
Every profiled table across every run, from GOVERNANCE.DATA_PROFILES (one row per column per profiling pass; tables profiled before V036 show from the profile store until they are profiled again). Filter by domain, table, run, tag and your bookmarks; cards or grid. The table drawer shows the scorecard, drift against the live table and against the previous pass, per-column null and distinct ratios and distributions, and actions: bookmark, re-profile, Soda and Great Expectations checks, mappings, start a model.
Compare any two passes
"Compare with" in the drawer puts the chosen pass next to the one shown, column by column: null rate and distinct values before and after, and what changed (type, a null jump of 10 points or more, distinct values moving more than half, semantic type, PII), with the row count change and how many columns changed, appeared or disappeared (GET /api/hub/profiles/columns?compare_to=).
Schedules
?section=schedules: profile a database.schema (every table, or a list) on a cron. Each schedule (GOVERNANCE.PROFILE_SCHEDULE, V041) is a Snowflake task PROFILE.PROF_<hash> that calls PROFILE.RUN_SCHEDULED_PROFILE (owner's rights: the owner role needs SELECT on the tables). A table whose columns, row count and last change are the same as last time reuses its profile unless "Profile every run" is on. The schedule shows the last run: profiled, unchanged and failed tables, and the tables whose new pass drifted from the one before, with the columns. Run now calls the same procedure.
Annotations
What people know about a column that the profiler cannot tell: description, business definition, PII class, semantic type, accepted values. Annotate a column from the drawer (only the fields you change are proposed; a newer proposal replaces a pending one). A data steward approves or rejects it in ?section=annotations (four eyes: not the person who proposed it; rejecting needs a note). An approved annotation (GOVERNANCE.PROFILE_ANNOTATION) overrides the profiler in the profile views and supersedes the previous one; when the table is an entity of its domain's approved model and has the column, it is also proposed to the model (Model Workbench, Proposals), so the model changes only through its own review.
Privileges
Reading and bookmarks: everyone signed in. PROFILE.RUN re-profile, schedule profiling, propose an annotation. KNOWLEDGE.EDIT (data stewards) approve or reject an annotation (never queued: the review is the approval).

How a model version is governed
Each domain has one canonical, versioned model (GOVERNANCE.DOMAIN_MODEL, versions in GOVERNANCE.MODEL_DESIGNS, V039). A version moves DRAFT, IN_REVIEW, APPROVED (PUBLISHED once its pull request is merged) or REJECTED; the version it replaces becomes SUPERSEDED. A model has at most one open version. Approval is four eyes, blocked by unresolved blockers, and a version with breaking changes needs the impact acknowledged. The approved version is applied to the domain registry (MODELING.APPLY_DOMAIN_MODEL, owner's rights), which every stage reads; registry ids are kept so mappings and STTM lines stay valid, retired entities are deactivated and a DOMAIN_VERSION snapshot is written; if that fails the approval stands and Review offers to apply it again. The deploy writes an APPROVED baseline (version 1) per domain from its registry. API under /api/hub/domain-models; these routes are never queued as change requests because the review is the approval.

Gates

  • Human gates: each *_REVIEW state moves to *_APPROVED only by a person with the matching approve privilege, or back to *_PENDING.

  • Mastered keys are resolved through the full cross-reference (never the STAGE delta), matching on the source key and the upper-cased source-system name; an unresolved record gets -1.
  • A domain has one Silver model and one Gold model in the Model Workbench (GOVERNANCE.DOMAIN_MODEL.LAYER, V053). Approving the Gold model registers its own tables in the target registry with LAYER = 'GOLD' (V054), so Gold runs can map into them; Silver runs and the domain pages keep seeing only Silver targets.
  • Domains Reltio masters (Company, Property) have their gold in gdp-dbt already; their dimensions are referenced by consumers, not rebuilt.

Lineage

/lineage traces a table or a column from Source to Gold, in either direction, and shows each layer as a swimlane: Source, Bronze (landed), Silver pre-MDM, MDM cross-reference, Silver post-MDM and Gold. Each hop lists how it happens: landed, mapped (the approved STTM expression), MDM match, golden record, resolved key, or built (gold generation). Edges come from SOURCE.LANDING_TABLE_REGISTRY, approved CONTRACT.STTM_LINE rows, the mastered-domain contracts and consumer target columns; a Gold run's approved STTM gives the Silver to Gold hops. It is linked from a run's code generation step and the domain's Medallion and MDM panel. Read only, for everyone signed in (GET /api/lineage/trace, GET /api/lineage/objects).

Onboarding a consumer domain (example: Availability)

Only Company and Property are mastered by Reltio. A new domain whose records refer to companies or properties, such as Availability, is a consumer: its Silver keeps the pre-MDM keys, and its Gold resolves them to the mastered dimensions. The pattern is the same for any consumer.

  1. Domain intake. Create the domain, add its sources, data model file and examples on the Sources tab. On the Lineage tab, in Medallion and MDM, choose Link to MDM and add Property (PROPERTY_CORE_SKEY to DIM_PROPERTY_SKEY) and Company (COMPANY_CORE_SKEY to DIM_COMPANY_SKEY). This needs DOMAIN.EDIT and is versioned with the domain.
  2. Silver Pipeline. Start a Silver run: Source Ingestion, Profiling, then Modeling. Because the domain is a consumer, field mapping and the STTM use the post-MDM skill, so the Silver hub carries the PROPERTY_CORE_SKEY and COMPANY_CORE_SKEY lookups next to the availability columns. Finish with Silver Code Generation and the quality lane.
  3. Gold Pipeline. After the Silver hub is loaded and Reltio has mastered the related companies and properties, start a Gold run for the domain and select the hub. On Modeling, propose the gold model: FACT_AVAILABILITY with DIM_PROPERTY_SKEY and DIM_COMPANY_SKEY resolved through the cross-reference, new dimensions for descriptors, and a bridge where an availability relates to several companies in different roles. Once it is approved in the Model Workbench, pick FACT_AVAILABILITY, approve the mapping and the STTM, then QA tests, Data Quality, Gold Code Generation, Validation and Code review. Start another Gold run for the bridge.
  4. Lineage. In /lineage, trace FACT_AVAILABILITY.DIM_PROPERTY_SKEY upstream: source record, landed table, Silver hub, the property's cross-reference row, the golden record and DIM_PROPERTY.

Check before you start: the domain's source systems exist in SHARED.REF_GDP_SOURCE_SYSTEM (the match uses the upper-cased system name), and the match rate on the Company and Property Medallion panels is acceptable for those systems. A low match rate means many gold rows will carry -1.

GitHub setup

Two separate GitHub connections, each with its own token:

Code repositories (read)

Indexes the client's dbt, SQL and Python code so AI steps can quote it and the Code page can show lineage. Uses a read-only token per repository, stored as a Snowflake PASSWORD secret used by a Snowflake Git repository object.

dbt publishing (write)

Pushes generated dbt to a new branch and opens a pull request. Uses one write token, stored as a Snowflake GENERIC_STRING secret, reached through an external access integration to api.github.com.

Use two different tokens: the read token can never push, and the write token never reaches the indexing clone. Both are fine-grained personal access tokens created at GitHub, Settings, Developer settings, Fine-grained tokens, limited to the client's repositories.

Part A. Connect a code repository

  1. Prerequisites. The platform is deployed. You hold INTEGRATION.MANAGE. Your Snowflake role can create secrets and git repositories in the CODE schema.
  2. Create a read-only token limited to the repository with Contents: Read (Metadata: Read is added automatically). A public repository needs no token.
  3. Make sure a git API integration exists. If none allows the repository's host, the connect drawer says "No usable Git integration allows <host>" and shows the SQL for an account admin: 
    CREATE API INTEGRATION GIT_CODE_CONTEXT
  API_PROVIDER = GIT_HTTPS_API
  API_ALLOWED_PREFIXES = ('https://github.com/<org>')
  ALLOWED_AUTHENTICATION_SECRETS = ALL
  ENABLED = TRUE;
GRANT USAGE ON INTEGRATION GIT_CODE_CONTEXT TO ROLE <your role>;
  4. Open Admin, Integrations, Code repositories, Connect repository and fill in:
    • Repository URL: the https address (not ssh).
    • Name: filled from the URL (letters, digits and underscores, starting with a letter).
    • Branch: default main.
    • Snowflake Git integration: pick the one that allows the host.
    • Credentials: New read-only token (paste it; any username, default token), an existing PASSWORD secret, or Public repository. You can also reuse a Git repository object that already exists in Snowflake; it keeps its own credentials and is never changed or dropped.
    • Domains it serves (none means all), paths to include or skip, and Index now.
  5. Connect. The platform creates the secret <DB>.CODE.<NAME>_GIT_TOKEN and the Git repository <DB>.CODE.<NAME>, fetches it, checks the branch and starts indexing. If the integration lists specific secrets instead of ALL, add the new secret to its ALLOWED_AUTHENTICATION_SECRETS.
  6. Schedule refreshes in the repository's Schedule tab (hourly, daily 06:00 UTC by default, weekdays, weekly, or a cron with time zone). This creates a Snowflake task CODE.REFRESH_<id>; your role needs CREATE TASK in CODE, warehouse USAGE and the account privilege EXECUTE TASK.
  7. Check it. The repository shows files, models and the last index run; Code search and lineage return results.

Branch switch: click the branch chip, Fetch, Switch (the index is rebuilt). Rotate credentials in the Credentials tab (Save and test). Disconnect removes the index and schedule; tick "Also drop the Snowflake Git repository and secret" to drop objects the platform created.

Part B. Set up dbt publishing (pull requests)

  1. Prerequisites. You hold ADMIN.DEPLOY. Your Snowflake role can create integrations on the account and secrets and network rules in CODEGEN. The dbt repository is connected as in Part A.
  2. Create a write token limited to the repositories that receive PRs, with Contents: Read and write and Pull requests: Read and write. A classic token needs the repo scope. The token owner must have write access to the repository.
  3. Admin, Integrations, Code repositories, card "Pull requests to GitHub": paste the token and choose Set up. The platform runs and logs:

  MODE = EGRESS TYPE = HOST_PORT VALUE_LIST = ('api.github.com');

  4. Test access on the card: it reads the repository and reports "push allowed", or that the token cannot push.
  5. Repository dbt settings (repository drawer, dbt workspace tab): Offer this repository to the dbt workspace; dbt project folder (one of the dbt_project.yml folders found by the index); Open the PR right after generating; Open PRs as drafts.
  6. Use it in a run (dbt step): choose Cut from (default the repository branch) and New branch (default feat/onboard-<run>; must differ), then Generate, then Push and open PR. The PR is recorded in CODEGEN.GIT_PUBLICATION and a compile-only DBT PROJECT is created from the branch.

Rotate the write token with "Rotate token" on the same card. Pull requests are GitHub only; other providers stay stage only.

Updating an environment

  1. Merge the pull request, then git pull origin main and reinstall dependencies if requirements.txt or package.json changed.
  2. Run the deploy command again. Only what changed is applied: new migrations, procedure, view, Cortex Search and agent files whose SQL changed, the code package when services/ changed (and the procedures that import it), and the seed when a domain pack, QA pack, skill or seeded setting changed. Everything else is listed as unchanged (skipped).
  3. Restart the API, the web app and the worker so they load the new code and any changed .env values.
  4. If the release notes mention the Airflow plugin, update plugins.zip in MWAA at the same time as the API (the event signature must match).
  5. Run the checks for the features the release touched.

With Docker, steps 1 and 3 become: set the new GDP_TAG and GDP_BUILD_SHA in docker/.env, pull (or build) the images, run the Snowflake deploy, then docker compose ... up -d, which recreates only the containers whose image changed.

Admin, Deploy does steps 2 from the browser with the signed-in role (needs ADMIN.DEPLOY). The API and web restart are still needed for code changes.
How the deploy knows what changed. CORE.DEPLOY_STATE holds a checksum of each step's rendered SQL (procedure, view, Cortex Search, agent and demo files), the code package name, the seed inputs and the GitHub publisher and Oracle refreshes, written only after the step succeeded, so a failed step runs again next time. When a migration is applied, views, Cortex Search, agents and the seed run again so they see the new tables. If an object was changed or dropped in Snowflake by hand, or silver tables were created since the last seed, re-apply everything with --force (or "Re-apply everything" in Admin, Deploy). The seed leaves the target tables of domains that have an approved Model Workbench version alone: the approved model is their source of truth; to bring a changed repository pack into such a domain, import it into a draft in the Model Workbench.
Never edit an applied migration. Each migration's checksum is recorded; a changed file stops the deploy. Add a new migration instead.

Production settings

  • Sign-in: AIP_AUTH=pat and AIP_ACCOUNT, so each person works under their own Snowflake identity. Set the same AIP_AUTH in the web app.
  • Worker identity: a key-pair service user with the OPS_SERVICE database role, warehouse usage and CORTEX_USER (AIP_SERVICE_USER, AIP_SERVICE_KEY_PATH, optional passphrase, role and warehouse).
  • Containers: run web, API and worker with docker/docker-compose.yml (Deploy with Docker). Compose keeps the API unpublished, restarts each container on failure and starts web and worker once the API is healthy.
  • Web: behind HTTPS on the public hostname. Without Docker: npm run build then npm run start, with AIP_API_URL set to the API's internal address.
  • API: private; only the web app talks to it. Without Docker: uvicorn bound to localhost or a private network.
  • Worker: restarts on failure. Running two copies is safe: leases let only one holder run each job.
  • Public URLs: the Jira callback, the Airflow ingest URL and the public base URL must use the public HTTPS origin, not localhost.
  • Secrets: prefer the host's secret manager or service environment over a .env file; values in the environment win over the file.

Rollback

  • Code and procedures: check out the previous release and run the deploy again; procedures and the services package are replaced. With Docker, set GDP_TAG back to the previous release and run up -d.
  • Migrations only move forward. To undo a schema change, write a new migration that reverses it.
  • Secrets: keep the previous key values until the rollback is confirmed; values sealed with a different key cannot be read.

Updating your local app

The Snowflake deploy updates Snowflake objects only; it never changes what localhost:3000 serves. After pulling new code:

  1. git checkout main and git pull origin main in the folder you run the app from.
  2. In apps/web: npm install, then npm run build before npm run start (next start serves the last build, not the current code). With npm run dev, delete .next and restart instead.
  3. Stop the old web server first: if port 3000 is still taken, a new server quietly starts on 3001 and the browser keeps showing the old one.
  4. Restart the API (uvicorn) so new routes load, then hard refresh the browser (Ctrl+Shift+R).

npm run doctor in apps/web checks all of this and says what to run. The running build is shown at the bottom of the sidebar and the account menu (Build <commit>), and /bff/version reports the web and API commits.

Generate a key

AIP_SECRET_KEY and JIRA_TOKEN_KEY must each be a long random value: at least 32 characters, different from each other, and different in every environment. Generate each one separately.

Windows PowerShell

[Convert]::ToBase64String((1..32 | ForEach-Object { Get-Random -Maximum 256 }))

This takes 32 random bytes and prints them as a 44-character Base64 string, for example a value ending in =. The = and any / or + are part of the key; copy the whole line.

Any system with Python

python -c "import secrets; print(secrets.token_urlsafe(32))"

macOS or Linux

openssl rand -base64 32
Keep keys stable. Store them in your team's password manager when you create them. Changing a key makes everything sealed with it unreadable: people reconnect Jira, admins re-enter push secrets.

Fill the .env file

  1. Create the file from the template (it lists every setting, with no values): 
    Copy-Item apps/api/.env.example apps/api/.env
    On macOS or Linux: cp apps/api/.env.example apps/api/.env.
  2. Confirm git ignores it before typing any secret: 
    git check-ignore -v apps/api/.env
    It must print the .gitignore line that matches. git status must not list the file.

11Known gaps

Found while writing this guide. Each needs a decision or a fix before a production rollout.

QA lead sign-off grant. CONTRACT.QA_SIGNOFF accepts inserts only from DATA_ENGINEER. A QA lead holding only the QA_ENGINEER database role cannot sign off until that grant is added (or they also get DATA_ENGINEER).
Fixed: run QA procedures for QA_ENGINEER. QA_SUITE, QA_ASK and QA_SAVE are now granted to QA_ENGINEER, and QA_SAVE to REVIEWER. Redeploy procedures to apply.
Change requests for viewers. Raising an approval request writes to GOVERNANCE.CHANGE_REQUEST with the requester's role; VIEWER cannot write there. Only DATA_ENGINEER holds REQUEST.CHANGES, so this matters only if that privilege is given to read-only roles.
Store edits wait for a second person. With "Store edits require approval" on (the default), every STTM Store edit and every DQ Store schedule change is a change request that the editor cannot approve, and every suite version needs a DQ_APPROVER who did not work on it, so each team needs at least one STTM_APPROVER and DQ_APPROVER other than its editors. Turn the setting off in Admin only if the stores should follow the run-page rules.
Procedures without grants. CODE.INDEX_REPO, CODEGEN.PUBLISH_DBT_PR and each ORACLE_RUN have no USAGE grants; they work for the owning role only. Grant USAGE to DATA_ENGINEER if others should run them directly.
Fixed: Jira token rows. Migration V033 adds the row access policy JIRA.OWN_ROWS: each person sees only their own USER_TOKEN and OAUTH_STATE rows; sessions with the PLATFORM_ADMIN database role see all. The Admin count of connected users therefore shows only yourself unless you are a platform admin.
Routing text. Admin says a DAG's own team wins over routing rules; the code applies routing rules first. Treat rules as the deciding source until the text is corrected.
Deploy default database. The deploy script defaults to AI_PLATFORM while the API defaults to DEV_AI_PLATFORM. Always pass --database.
Copilot conversations in dev sign-in. With AIP_AUTH=dev every browser user is the same Snowflake user, so copilot conversations and their drafts are shared between them. With pat they are private to each person.
Unused table. AUDIT.AGENT_RUN exists but nothing writes to it yet.
