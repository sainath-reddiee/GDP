Operating guide

GDP Agent Platform Guidebook

Everything needed to run the platform: who can do what, which Snowflake grants back it, how to configure each feature, and what every table holds. Written for data engineers, QA, support engineers and platform admins.

01How access works

Every action passes two independent checks. Both must allow it.

1. App governance

The API maps each call to a privilege (for example STTM.APPROVE). A user's privileges are the union of their app roles, including inherited roles. Roles live in the GOVERNANCE schema and are managed in Admin, Access and governance.

Each call is decided as Allow, Request (HTTP 202, queued in Approvals) or Forbid (HTTP 403).

2. Snowflake grants

The call then runs on a Snowflake session. Snowflake enforces its own object grants on the session's current role. A user can switch that role with the role selector at the bottom of the sidebar; only roles granted to the user are offered.

An approved request is replayed under the approver's session, so the approver's grants apply.

Decision rules

  • Allow when the call needs no privilege, or the user holds it and its approval policy is off (or the user may self-approve).
  • Request when an approval policy is active and the user holds REQUEST.CHANGES or the privilege itself under a four-eyes policy. The UI shows the action and says it was sent for approval.
  • Forbid otherwise, with the message "needs the X privilege".
  • A changing call (POST, PUT, DELETE) that no rule names needs RUN.OPERATE. A GET that no rule names is open to every signed-in user.
  • Role changes take effect within about a minute (60 second cache).
  • Until migration V020 is deployed, governance is not enforced.
First admin. When nobody holds any role yet, the first person to sign in, plus everyone listed in AIP_SUPER_ADMINS, becomes SUPER_ADMIN. Everyone else without a role gets the default role, VIEWER unless changed in Admin.

02Setup order

For a new environment, do these in order. Each later feature depends on the earlier steps.

  1. Deploy Snowflake objects. Run python infrastructure/deploy_snowflake.py --connection <name> --database DEV_AI_PLATFORM --warehouse DBT_WH with a role that can create schemas, procedures, stages, Cortex Search services and agents. Always pass --database: the script's default (AI_PLATFORM) differs from the API's (DEV_AI_PLATFORM).
  2. Grant database roles to account roles. See Who gets what. Also grant warehouse USAGE and SNOWFLAKE.CORTEX_USER.
  3. Configure the API. Copy apps/api/.env.example to apps/api/.env (gitignored) and fill it in. See Environment variables.
  4. Start the API and web app, then sign in once with an admin account so governance bootstraps. Set AIP_SUPER_ADMINS first if the first sign-in should not be you.
  5. Assign app roles in Admin, Access and governance.
  6. Connect integrations in Admin, Integrations: code repositories and GitHub publishing, Jira, Airflow, Incidents.
  7. Start the worker (python -m app.worker in apps/api) if you use Pipelines or Incidents.

Gates

  • Human gates: each *_REVIEW state moves to *_APPROVED only by a person with the matching approve privilege, or back to *_PENDING.
  • After the STTM is approved, three lanes run in parallel: Data Quality (every check decided, at least one approved), QA (signed off on the current STTM version), Validation (passed). Code review stays locked until all three are complete.
  • QA sign-off: allowed after STTM approval and before code approval. A rejection needs a note. If critical or high tests fail, approval needs an override with a reason of at least 15 characters.
  • Forcing a state needs ADMIN.DEPLOY.

Incidents

Same error again adds an occurrence. A repeat within the reopen window (24 h) reopens. The next successful run resolves automatically. Failures one or two DAGs downstream within 2 hours become children with no ticket and no alert.
Routing
Rules by priority (DAG pattern, tag, owner, environment) choose the team, then the DAG's own team, otherwise unrouted. Unrouted incidents get a ticket in the default project and no Teams card.
Notifications
Teams Adaptive Cards with Acknowledge, Open incident, Open Jira and Open log links; at most 10 cards per team per 10 minutes, then a summary. Escalation after the team's minutes (P1 at once), repeating at double the interval, up to 3 times.
AI
Diagnosis with cause, evidence cited from the context, confidence, safe-to-retry, fix steps and blast radius; automatic for new P1 to P3 incidents. Ask about an incident; postmortem draft. A resolution note of 20 characters or more becomes knowledge for later diagnoses.
Retry
Always previewed first with a dry run. A retry marked unsafe needs an override reason of at least 15 characters.
Privileges
OPS.VIEW view. OPS.OPERATE acknowledge, assign, resolve, mute, reopen, ticket, retry, bulk. AI.USE diagnose, ask, postmortem. INTEGRATION.MANAGE teams, webhooks, routing, settings.

GitHub setup

Two separate GitHub connections, each with its own token:

Code repositories (read)

Indexes the client's dbt, SQL and Python code so AI steps can quote it and the Code page can show lineage. Uses a read-only token per repository, stored as a Snowflake PASSWORD secret used by a Snowflake Git repository object.

dbt publishing (write)

Pushes generated dbt to a new branch and opens a pull request. Uses one write token, stored as a Snowflake GENERIC_STRING secret, reached through an external access integration to api.github.com.

Use two different tokens: the read token can never push, and the write token never reaches the indexing clone. Both are fine-grained personal access tokens created at GitHub, Settings, Developer settings, Fine-grained tokens, limited to the client's repositories.

Part A. Connect a code repository

  1. Prerequisites. The platform is deployed. You hold INTEGRATION.MANAGE. Your Snowflake role can create secrets and git repositories in the CODE schema.
  2. Create a read-only token limited to the repository with Contents: Read (Metadata: Read is added automatically). A public repository needs no token.
  3. Make sure a git API integration exists. If none allows the repository's host, the connect drawer says "No usable Git integration allows <host>" and shows the SQL for an account admin: 
    CREATE API INTEGRATION GIT_CODE_CONTEXT
  API_PROVIDER = GIT_HTTPS_API
  API_ALLOWED_PREFIXES = ('https://github.com/<org>')
  ALLOWED_AUTHENTICATION_SECRETS = ALL
  ENABLED = TRUE;
GRANT USAGE ON INTEGRATION GIT_CODE_CONTEXT TO ROLE <your role>;
  4. Open Admin, Integrations, Code repositories, Connect repository and fill in:
    • Repository URL: the https address (not ssh).
    • Name: filled from the URL (letters, digits and underscores, starting with a letter).
    • Branch: default main.
    • Snowflake Git integration: pick the one that allows the host.
    • Credentials: New read-only token (paste it; any username, default token), an existing PASSWORD secret, or Public repository. You can also reuse a Git repository object that already exists in Snowflake; it keeps its own credentials and is never changed or dropped.
    • Domains it serves (none means all), paths to include or skip, and Index now.
  5. Connect. The platform creates the secret <DB>.CODE.<NAME>_GIT_TOKEN and the Git repository <DB>.CODE.<NAME>, fetches it, checks the branch and starts indexing. If the integration lists specific secrets instead of ALL, add the new secret to its ALLOWED_AUTHENTICATION_SECRETS.
  6. Schedule refreshes in the repository's Schedule tab (hourly, daily 06:00 UTC by default, weekdays, weekly, or a cron with time zone). This creates a Snowflake task CODE.REFRESH_<id>; your role needs CREATE TASK in CODE, warehouse USAGE and the account privilege EXECUTE TASK.
  7. Check it. The repository shows files, models and the last index run; Code search and lineage return results.

Branch switch: click the branch chip, Fetch, Switch (the index is rebuilt). Rotate credentials in the Credentials tab (Save and test). Disconnect removes the index and schedule; tick "Also drop the Snowflake Git repository and secret" to drop objects the platform created.

Part B. Set up dbt publishing (pull requests)

  1. Prerequisites. You hold ADMIN.DEPLOY. Your Snowflake role can create integrations on the account and secrets and network rules in CODEGEN. The dbt repository is connected as in Part A.
  2. Create a write token limited to the repositories that receive PRs, with Contents: Read and write and Pull requests: Read and write. A classic token needs the repo scope. The token owner must have write access to the repository.
  3. Admin, Integrations, Code repositories, card "Pull requests to GitHub": paste the token and choose Set up. The platform runs and logs:

Rotate the write token with "Rotate token" on the same card. Pull requests are GitHub only; other providers stay stage only.

Updating an environment

  1. Merge the pull request, then git pull origin main and reinstall dependencies if requirements.txt or package.json changed.
  2. Run the deploy command again. Only new migrations run; procedures and code are refreshed every time.
  3. Restart the API, the web app and the worker so they load the new code and any changed .env values.
  4. If the release notes mention the Airflow plugin, update plugins.zip in MWAA at the same time as the API (the event signature must match).
  5. Run the checks for the features the release touched.
Admin, Deploy does steps 2 from the browser with the signed-in role (needs ADMIN.DEPLOY). The API and web restart are still needed for code changes.
Never edit an applied migration. Each migration's checksum is recorded; a changed file stops the deploy. Add a new migration instead.

Production settings

  • Sign-in: AIP_AUTH=pat and AIP_ACCOUNT, so each person works under their own Snowflake identity. Set the same AIP_AUTH in the web app.
  • Worker identity: a key-pair service user with the OPS_SERVICE database role, warehouse usage and CORTEX_USER (AIP_SERVICE_USER, AIP_SERVICE_KEY_PATH, optional passphrase, role and warehouse).
  • Web: npm run build then npm run start, behind HTTPS. Set AIP_API_URL to the API's internal address.
  • API: uvicorn behind a reverse proxy on HTTPS; keep it private and let the web app proxy to it.
  • Worker: run as a service that restarts on failure. Running two copies is safe: leases let only one holder run each job.
  • Public URLs: the Jira callback, the Airflow ingest URL and the Teams public base URL must use the public HTTPS origin, not localhost.
  • Secrets: prefer the host's secret manager or service environment over a .env file; values in the environment win over the file.

Rollback

  • Code and procedures: check out the previous release and run the deploy again; procedures and the services package are replaced.
  • Migrations only move forward. To undo a schema change, write a new migration that reverses it.
  • Secrets: keep the previous key values until the rollback is confirmed; values sealed with a different key cannot be read.

Generate a key

AIP_SECRET_KEY and JIRA_TOKEN_KEY must each be a long random value: at least 32 characters, different from each other, and different in every environment. Generate each one separately.

Windows PowerShell

[Convert]::ToBase64String((1..32 | ForEach-Object { Get-Random -Maximum 256 }))

This takes 32 random bytes and prints them as a 44-character Base64 string, for example a value ending in =. The = and any / or + are part of the key; copy the whole line.

Any system with Python

python -c "import secrets; print(secrets.token_urlsafe(32))"

macOS or Linux

openssl rand -base64 32
Keep keys stable. Store them in your team's password manager when you create them. Changing a key makes everything sealed with it unreadable: people reconnect Jira, admins re-enter webhooks and push secrets.

    It must print the .gitignore line that matches. git status must not list the file.

11Known gaps

Found while writing this guide. Each needs a decision or a fix before a production rollout.

QA lead sign-off grant. CONTRACT.QA_SIGNOFF accepts inserts only from DATA_ENGINEER. A QA lead holding only the QA_ENGINEER database role cannot sign off until that grant is added (or they also get DATA_ENGINEER).
Fixed: run QA procedures for QA_ENGINEER. QA_SUITE, QA_ASK and QA_SAVE are now granted to QA_ENGINEER, and QA_SAVE to REVIEWER. Redeploy procedures to apply.
Change requests for viewers. Raising an approval request writes to GOVERNANCE.CHANGE_REQUEST with the requester's role; VIEWER cannot write there. Only DATA_ENGINEER holds REQUEST.CHANGES, so this matters only if that privilege is given to read-only roles.
Procedures without grants. CODE.INDEX_REPO, CODEGEN.PUBLISH_DBT_PR and each ORACLE_RUN have no USAGE grants; they work for the owning role only. Grant USAGE to DATA_ENGINEER if others should run them directly.
Fixed: Jira token rows. Migration V033 adds the row access policy JIRA.OWN_ROWS: each person sees only their own USER_TOKEN and OAUTH_STATE rows; sessions with the PLATFORM_ADMIN database role see all. The Admin count of connected users therefore shows only yourself unless you are a platform admin.
Routing text. Admin says a DAG's own team wins over routing rules; the code applies routing rules first. Treat rules as the deciding source until the text is corrected.
Deploy default database. The deploy script defaults to AI_PLATFORM while the API defaults to DEV_AI_PLATFORM. Always pass --database.
Unused table. AUDIT.AGENT_RUN exists but nothing writes to it yet.
